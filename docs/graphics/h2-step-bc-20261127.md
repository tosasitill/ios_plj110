# H2 step b/c, priming verdict, and the remaining GPU roadmap — 2026-11-27

Companion to `gpu-optimization-headroom.md` (the rev231-era evaluation).
That report predates M3 priming, the resident/parked group, live
map/unmap, H1 and H2 step a; this note records what changed, what this
branch landed, and what is still open, with the same evidence labels
(DEVICE = a log the device produced, CODE = read from the tree).

## 1. Priming (M3): the rev287 verdict

Question: did pipeline priming ever work on device?

- rev286 (DEVICE, `~/gpu-r286-20261127.txt`): the frontend binary
  contained the priming code and it ran — backboardd and SpringBoard
  both logged `x9-prime: no inventory (list=none)` because the
  primelist was not packaged yet. Code present, inventory absent:
  priming was a correct no-op.
- rev287 (DEVICE, `~/gpu-r287-20261127.txt`): zero `x9-prime` lines in
  the whole session, and `strings` on the shipped
  `X9GeneralMetal287.bundle/X9GeneralMetal` confirms why: **the binary
  contains no priming code at all**. The plugin build compiles the
  frontend from `.local/x9/MaliMetal/X9/General`, a symlink into the
  main checkout, which sat at a pre-priming state; only the primelist
  file had been re-applied there. The bundle therefore shipped the
  inventory next to a binary that could never read it. It was not the
  quiet gate: with code present, an empty inventory logs immediately
  and a found inventory now logs `x9-prime: begin` at pass start (added
  this branch), so a silent session can no longer be ambiguous.
- Whether a full pass completes and actually warms pipelines is still
  unobserved on device: no build with both halves present has booted.
  The trigger chain in current source is audited sound (CODE):
  `x9_prime_start` fires at device creation only when the render
  backend probed ready; `gCommits` is incremented in NBCommandBuffer
  commit; the quiet gate opens on the first 250 ms window with <= 8
  commits and is deadline-forced at 90 s per library.

Fix landed: `check-priming-consistency.py` refuses
inventory-without-code for both the frontend source dir and the built
bundle (marker bytes verified against the shipped 286/287 binaries);
`build-general-metal.py` runs it before compiling and after signing.
Code-without-inventory stays legal with a loud warning (the deliberate
rev286 state). Priming also gained begin/deadline log lines so the
next round can tell "code alive, gate shut" from "no code".

## 2. H2 step b — landed (log only, `x9_coh_probe=1`)

Step a sampled only the first/last atom of at most 4 skipped resources
per job into one pooled counter pair: interior staleness was invisible
and "stale=0" had no denominator. Step b replaces the selection with
`x9_render_coh_pick_atoms` (pure arithmetic, host-tested in
`x9/tools/test_x9_coh_pick.py`): strided picks rotated per resource,
so over one rotation cycle every atom of a written range is sampled
equally often. Verdicts are per class — native BOs vs imported
(IOSurface) BOs — with eligible-vs-sampled resource accounting in the
periodic `X9 RENDER COH-PROBE` line. Bounds unchanged in spirit: <= 4
resources and <= 16 atoms per job, post phase only, and the sampler
still CIVACs every atom it touches (a probe build maintains more than
production, never less). The skip itself is untouched.

## 3. H2 step c — accounting landed; the proof is designed, not landed

The pre phase skips the same classes' cleans in the CPU->GPU direction
on the same ACE-Lite snoop assumption. No CPU-side observation can
falsify that direction: the probe's trick (read plainly, then CIVAC
and re-read) works only for data the GPU wrote and the CPU reads. So
step c counts the skipped pre-phase bytes per class under the probe
gate and the verdict line reports them as **assumed, not probed**.

The designed proof is a frontend readback harness, reusing the
benchmark's real-pipeline path (`native_bridge_metal_benchmark`
already runs dummy draws through the whole stack):

1. Allocate a test BO; the CPU writes a known pattern through its
   cached mapping; arrange for the job that consumes it to take the
   coherent pre-phase skip for that BO (the skip is per-resource in
   the kernel; the harness needs a way to force it for the test BO
   only — e.g. run the whole harness under `x9_gpu_coherent=1`, which
   is already the default, and use an exposed cached BO).
2. Run a copy compute pipeline (pattern in, identity copy out to a
   second BO) through the normal frontend path.
3. Read the output back taking the post-phase skip as well, and
   compare against the pattern on the CPU.
4. A mismatch in step 3 with step b simultaneously reporting stale=0
   on the output BO isolates the failure to the CPU->GPU direction.

Not landed here: it needs an on-device run to mean anything, and
wiring a self-test into the production frontend without a device to
validate it against would be exactly the kind of unverified change
this line of work exists to avoid. The kernel-side accounting is the
part that is safe to land blind.

## 4. M4 step b — designed in the source, not landed

`X9MetalFrameMetrics.inc` (step a) states it plainly: the kernel has
per-job GPU timestamps (`X9 RENDER GPUTS`, `x9gt=1`) but
`X9RenderCompletion` carries no timestamps, so joining GPU time to
the frontend stage chain needs an ABI extension to the completion
record, and a present-side FPS belongs to the kernel display path.
That is a three-party ABI change (kernel, PanVK backend, frontend)
and should land as its own gated step with the headroom report's P3
as the acceptance frame — not folded into a coherency branch.

## 5. Remaining roadmap (headroom items, state refreshed)

- **P0-A submission decoupling** — still the largest single item
  (`wait` was 51% of job service time at rev231). Design exists in
  `submission-decoupling-design.md`; the parked-group and pipelining
  work since then changed the shape but not the synchronous
  submit-and-wait core. High risk; needs its own A/B round.
- **P0-C address-space teardown** — mostly landed since the headroom
  report: the resident group (park) and live map/unmap removed the
  per-job install/detach for the common path. What remains is the
  retire path's whole-AS flush semantics on context switches.
- **P1-A BO pool with aging** — open. The alloc-time full-length
  `dc civac` scrub of every fresh WC BO (headroom rule (a) residual)
  is the pool's clearest first dividend.
- **P1-B mapping economics** — open: one IOKit round-trip per map op
  from PanVK, linear handle scans, 4 KiB pages only (vendor enables
  2 MiB blocks on this GPU family).
- **P2-A transient/memoryless attachments** — open, and still gated
  on attributing the Control Center platter defect first.
- **P2-B damage-aware present** — open (display path, Task 7).
- **P2-C worker QoS / suspend timeouts** — CPU-side scene policy
  landed separately (`x9sched`); GPU worker priority and the 1 s CSG
  halt bound vs the vendor's shortened suspend timeout remain open.

## 6. Next device round — what to look for

Priming (needs a candidate built from a tree whose main-checkout
General dir matches, which the new build gate now enforces):
1. Early in the log, per desktop process: `x9-prime: begin list=...
   libraries=8 build=...`. Absence of any `x9-prime` line with the
   new gate in the build means the frontend did not load — a
   different problem than 287's.
2. Within ~4 minutes idle: `x9-prime: pass ... finished=8 failed=0
   made=<N>` with N > 0. `quiet deadline` lines instead mean the
   desktop never went quiet; the pass still proceeds, just busy.
3. `failed>0` or `finished<8`: read which library — the pass line is
   the summary; per-library failure detail is the follow-up.

H2 (boot with `x9_coh_probe=1`, use the desktop normally):
4. `X9 RENDER COH-PROBE` lines with `resources=S/E` where S approaches
   E over time, atoms growing, and per-class stale counts. Any
   `stale>0` falsifies the snoop claim **for that class only** — the
   follow-up would be to narrow the coherent skip to the surviving
   class, which the per-class counters now make a one-line change.
5. `pre_skip_bytes` growth documents how much maintenance the
   unproven CPU->GPU direction is skipping; it is exposure
   accounting, not evidence.
